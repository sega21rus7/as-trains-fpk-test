# Правила локального проекта

Эти правила действуют для всего репозитория. Вложенный `AGENTS.md` может
уточнять правила для своего каталога.

## Принципы работы

- Перед изменениями изучать существующий код, конфигурацию и тесты.
- Следовать текущим соглашениям проекта, если задача явно не требует их изменить.
- Ограничивать изменения областью текущей задачи и не выполнять несвязанный рефакторинг.
- Сначала искать существующий компонент, утилиту, стиль или тип, пригодный для переиспользования.
- Не изменять публичный API компонентов без необходимости. Если изменение необходимо, явно указать причину.
- Не изменять конфигурацию сборки, линтера и тестов, если этого не требует задача.
- Не изменять и не удалять пользовательские правки, не относящиеся к задаче.
- Не редактировать вручную `package-lock.json`.
- Не изменять содержимое `node_modules`, `dist` и `coverage`.

## Технологии

- Использовать версии React, TypeScript и ESLint, зафиксированные в `package.json` и `package-lock.json`.
- Не обновлять зависимости только ради перехода на более новую версию.
- Для сборки и локальной разработки использовать Vite.
- Писать компоненты React только как функциональные компоненты и использовать хуки.
- Для работы с формами использовать `react-hook-form`, включая регистрацию полей, валидацию, отправку и сброс состояния формы.
- Для каждого компонента объявлять тип пропсов и типизировать компонент через `React.FC<TProps>`:

```tsx
type TProps = {};

const Component: React.FC<TProps> = () => {};
```

- Для тестирования использовать Jest и React Testing Library.
- Для компонента с собственной логикой или пользовательским поведением рядом с его файлом создавать тест с именем `Component.test.tsx` (например, для `TodoForm.tsx` — `TodoForm.test.tsx`). Простейший презентационный компонент может проверяться через тест родительского сценария.
- В тестах проверять поведение компонента с точки зрения пользователя: отображение, пользовательские действия, вызовы переданных колбэков и граничные состояния.
- Для взаимодействия с интерфейсом использовать запросы React Testing Library по доступным ролям, названиям и тексту; не привязывать тесты к CSS-классам и внутренней реализации компонента.
- Пользовательские действия выполнять через `@testing-library/user-event`, а `fireEvent` использовать только там, где это необходимо, например при работе с таймерами или отдельными DOM-событиями.
- Каждый тест должен быть независимым: очищать моки, таймеры, `localStorage` и другое изменяемое окружение в `beforeEach` или `afterEach`, если компонент с ним работает.
- Для Jest включать глобальную очистку моков через `clearMocks: true` в конфигурации и не дублировать `jest.clearAllMocks()` в каждом тесте.
- Для стилей использовать SCSS Modules.

## TypeScript

- Соблюдать строгую типизацию.
- Не использовать `any`. Если избежать его нельзя, добавить краткое обоснование рядом с использованием.
- Не использовать утверждение типа (`as`), оператор non-null assertion (`!`), `@ts-ignore` и `@ts-expect-error` для сокрытия ошибок типов без обоснования.
- Для внешних данных сначала проверять структуру, а затем использовать типизированное значение.
- Не дублировать типы. Общие типы выносить отдельно, когда они используются в нескольких местах.

## React и архитектура

- Не помещать сложную бизнес-логику непосредственно в JSX.
- Повторно используемую логику выносить в функции или пользовательские хуки.
- Не хранить в состоянии данные, которые можно вычислить из props или другого состояния.
- Не использовать `useEffect` для вычислений, которые можно выполнить во время рендера или обработчика события.
- Не добавлять `useMemo`, `useCallback` и `React.memo` без измеримой необходимости.
- Для списков использовать стабильные ключи, не зависящие от позиции элемента.
- Для асинхронных данных обрабатывать состояния загрузки, ошибки и отсутствия данных.

## Структура проекта

Исходный код размещать в каталоге `src` со следующей структурой:

```text
src/
  components/
  pages/
  utils/
  styles/
  App/
```

- Создавать только те каталоги, которые действительно нужны проекту.
- Переиспользуемые компоненты размещать в `src/components`.
- Страницы и компоненты уровня маршрута размещать в `src/pages`.
- Общие чистые функции размещать в `src/utils`.
- Тесты и SCSS Module компонента размещать рядом с его исходным файлом.

## Стили и интерфейс

- Использовать SCSS Modules для локальных стилей и `src/styles` для глобальных стилей.
- Не использовать inline-стили без необходимости.
- Использовать семантические HTML-элементы.
- Интерактивные элементы должны быть доступны с клавиатуры и иметь понятное доступное имя.
- Не использовать `div` или `span` вместо кнопок и ссылок.
- Проверять интерфейс на desktop- и mobile-размерах.
- Не допускать горизонтальной прокрутки страницы без явной причины.

## Зависимости

- Не добавлять и не обновлять зависимости без необходимости.
- Перед добавлением пакета проверить, нельзя ли решить задачу средствами уже установленных зависимостей или Web API.
- Если новая зависимость необходима, объяснить её назначение в итоговом сообщении.
- Устанавливать зависимости через npm, сохраняя согласованность `package.json` и `package-lock.json`.
- Для установки существующих зависимостей использовать `npm ci`.

## Документация

- Для каждого проекта создавать `README.md`.
- Описание проекта и инструкции в `README.md` писать на русском языке.
- Обновлять `README.md`, если изменились требования, установка, команды запуска или пользовательский сценарий.

## Настройки VS Code

В каждом проекте создавать файл `.vscode/settings.json` со следующим содержимым:

```json
{
  "editor.formatOnSave": true,
  "editor.tabSize": 2,
  "eslint.format.enable": true,
  "editor.codeActionsOnSave": {
    "source.fixAll.eslint": "explicit"
  }
}
```

## Команды package.json

В секцию `scripts` файла `package.json` добавлять следующие команды:

```json
{
  "start": "npm run dev",
  "dev": "vite --open",
  "typecheck": "tsc --noEmit",
  "build": "npm run typecheck && vite build",
  "test": "jest",
  "test:coverage": "jest --coverage",
  "lint": "eslint --cache --ext=js,jsx,ts,tsx src",
  "lint:fix": "eslint --cache --ext=js,jsx,ts,tsx src --fix"
}
```

## Тестирование

- Добавлять или обновлять тесты для нового и изменённого поведения.
- Для исправления ошибки по возможности сначала добавлять тест, воспроизводящий ошибку.
- Не ограничиваться snapshot-тестами и не проверять детали реализации или внутреннее состояние компонента.
- Не использовать произвольные задержки; ожидать результат через асинхронные методы React Testing Library.
- Мокать только внешние границы: сеть, время, хранилище и сторонние API.
- Не снижать существующее покрытие изменённой функциональности.

## Безопасность

- Не добавлять в репозиторий секреты, токены, пароли и локальные `.env`-файлы.
- Не выводить секретные значения в логи и сообщения об ошибках.
- Не использовать непроверенные внешние данные через `dangerouslySetInnerHTML`.

## Ограничения выполнения

- Не запускать dev server, если это не требуется для проверки пользовательского интерфейса.
- При автоматической проверке не открывать браузер автоматически.
- После проверки останавливать запущенные серверы и фоновые процессы.
- Не выполнять разрушительные команды и не удалять пользовательские файлы без явного запроса.
- Для документационных и других не затрагивающих выполнение изменений запускать только применимые проверки.

## Проверка после выполнения задач

- Перед завершением программных изменений выполнять все применимые автоматические проверки: `npm test -- --runInBand`, `npm run lint`, `npm run typecheck` и `npm run build`.
- Если задача затрагивает пользовательский интерфейс, запускать приложение и проверять основной пользовательский сценарий в реальном браузере с помощью Playwright или Chrome, включая отсутствие ошибок в консоли браузера.
- При изменении интерфейса дополнительно проверять desktop- и mobile-размеры, управление с клавиатуры и доступные имена интерактивных элементов.
- Не считать задачу завершённой, пока проверки не пройдены. Если какую-либо проверку невозможно выполнить, явно указать причину.

## Definition of Done

Задача считается завершённой, если:

- реализовано только запрошенное поведение;
- отсутствуют ошибки TypeScript и ESLint;
- применимые тесты и production-сборка проходят;
- новое или изменённое поведение покрыто тестами;
- публичный API не изменён без необходимости;
- не добавлены необоснованные зависимости;
- изменённый интерфейс проверен на адаптивность и базовую доступность;
- в итоговом сообщении перечислены изменения, выполненные проверки и известные ограничения.
