# План разработки веб-прототипа «Витрина туристских поездов»

## 1. Цель и границы задачи

Сделать одностраничное приложение на React и TypeScript, которое читает 5 поездов из локального `trains.json`, показывает их в виде каталога, позволяет искать и фильтровать предложения, а также открывать подробную карточку выбранного поезда.

Прототип работает полностью на клиенте, без сервера и базы данных. Покупка билета не реализуется внутри приложения: кнопка переводит пользователя по значению `buy_url` во внешнюю систему в новой вкладке.

Проектировать интерфейс с применением `taste-skill`: сначала определить характер продукта и аудиторию, затем зафиксировать дизайн-параметры и только после этого выбирать композицию, цвет, типографику и движение. Правила скилла применять контекстно: это продуктовый каталог с фильтрами и модальным сценарием, поэтому декоративные приёмы посадочных страниц не должны ухудшать поиск, сравнение маршрутов и доступность.

## 2. Что уже есть в проекте

- Перед выполнением плана локально установить skill `design-taste-frontend` в `.agents/skills/design-taste-frontend`; Codex должен обнаруживать его как репозиторный skill при работе из этого проекта.
- React + TypeScript + Vite.
- SCSS и поддержка SCSS Modules.
- Jest, React Testing Library и `user-event`.
- Файл `trains.json` с массивом из 5 поездов.
- Стартовая страница `Hello World`, которую нужно заменить интерфейсом витрины.

Новые библиотеки для выполнения задачи не требуются. `taste-skill` используется как метод проектирования и критерий визуальной проверки, а не как runtime-зависимость. Реализацию сохранить на React, Vite и SCSS Modules; иконки не добавлять, если действие можно ясно назвать текстом.

### 2.1. Design read и визуальная система

**Design Read:** продуктовая витрина туристских поездов для широкой русскоязычной аудитории, с уверенным, спокойным и доверительным языком железнодорожного путешествия; визуальная основа - собственная система на SCSS Modules с опорой на фирменный красный цвет ФПК, крупную гротескную типографику и редакционную фотографию.

Режим проектирования: greenfield для интерфейса поверх готовых данных. Это не редизайн существующего сайта, поэтому не нужно переносить чужую информационную архитектуру, но нельзя выдумывать сведения о маршрутах, ценах и датах.

Зафиксировать параметры `taste-skill`:

- `DESIGN_VARIANCE: 6` - асимметричный hero и ритмичная сетка карточек делают витрину выразительной, но каталог остаётся предсказуемым;
- `MOTION_INTENSITY: 3` - только функциональные hover, focus, active и мягкие переходы состояний без scroll-hijack, параллакса и бесконечной анимации;
- `VISUAL_DENSITY: 6` - на экране достаточно данных для сравнения поездов, при этом заголовки, фильтры и карточки сохраняют воздух.

Система визуальных ограничений:

- одна светлая/тёмная тема на всю страницу с системным переключением через `prefers-color-scheme`, без инверсии отдельных секций;
- одна акцентная семья: фирменный красный и его контрастные состояния; не добавлять фиолетовые glow-эффекты и случайные дополнительные акценты;
- единая геометрия: радиус около 16 px для крупных поверхностей, 12 px для полей и кнопок, `999px` только для тегов;
- гротескная системная типографика без подключения внешнего шрифта, без декоративного serif и без смешения гарнитур внутри заголовка;
- реальные данные и реальная фотография вместо фальшивых UI-мокапов, декоративных SVG и выдуманных характеристик;
- карточки использовать потому, что они являются самостоятельными выбираемыми сущностями каталога; внутри карточек и модального окна иерархию строить в первую очередь отступами, типографикой и редкими разделителями.

## 4. Структура интерфейса

### 4.1. Верхняя часть страницы

- Асимметричный split hero: слева название «Витрина туристских поездов» и короткое пояснение, справа широкая фотография пассажирского поезда в пути.
- Hero должен помещаться в первый экран на desktop: заголовок не более двух строк, пояснение не более 20 слов и четырёх строк, верхний отступ не более 6 rem.
- Текстовый стек hero ограничить названием направления/бренда, заголовком и пояснением. Не добавлять scroll cue, номер версии, декоративную строку характеристик, список преимуществ или дублирующий CTA.
- Использовать подготовленный локальный hero-asset `public/train-hero.jpg` с правдивым нейтральным alt-текстом, фиксированными размерами и приоритетной загрузкой. Не назначать фотографию конкретному маршруту и не добавлять изображения в карточки поездов, потому что исходные данные не связывают фото с конкретными предложениями.
- Визуальный стиль: светлая нейтральная поверхность, фирменный красный акцент, крупная гротескная типографика, спокойная железнодорожная фотография. Не использовать generic glassmorphism, gradient text, внешние glow, декоративные линии и фальшивые схемы маршрутов в hero.

### 4.2. Панель поиска и фильтров

- Поле поиска по названию поезда.
- Выпадающий список региона со значением «Все регионы».
- Выпадающий список месяца со значением «Все месяцы».
- Кнопка сброса, которая очищает поиск и оба фильтра.
- Счётчик найденных поездов.
- Панель располагается на отдельной приподнятой поверхности, частично перекрывающей низ hero. Эффект полупрозрачности допустим только при сохранении контраста; для `prefers-reduced-transparency` предусмотреть сплошной фон.

Правила работы:

- поиск не зависит от регистра и игнорирует пробелы по краям;
- фильтры региона, месяца и строка поиска применяются одновременно;
- поезд соответствует месяцу, если хотя бы одна его дата отправления попадает в выбранный `YYYY-MM`;
- при выбранном месяце в превью показывается первая дата этого поезда внутри выбранного месяца;
- без фильтра месяца показывается ближайшая дата, которая не раньше текущего дня;
- если будущих дат нет, выводится понятный текст «Даты уточняются»;
- при нулевом результате показывается пустое состояние с предложением сбросить фильтры.
- все `label`, значения, placeholder, рамки, focus ring и сообщения должны проходить WCAG AA; placeholder не заменяет видимый `label`;
- изменение фильтров не сопровождается декоративной анимацией: результат обновляется сразу, а счётчик объявляется ненавязчивой live-областью.

### 4.3. Каталог поездов

Для каждого поезда сделать семантическую карточку, в которой отображаются:

- название;
- регион;
- маршрут в формате «первый город → последний город» строго по данным;
- длительность с корректным склонением;
- ближайшая или релевантная выбранному месяцу дата отправления;
- цена в формате «от 24 900 ₽»;
- краткое действие «Подробнее».

В текущих данных некоторые маршруты начинаются и заканчиваются в Москве, поэтому формат может выглядеть как «Москва → Москва». Это соответствует условию «первый → последний город»; промежуточные точки будут полностью видны в подробной карточке.

Карточка целиком либо её явная кнопка должна открывать подробности. Интерактивность следует реализовать настоящими кнопками/ссылками, без кликабельных `div`.

Композиция каталога по `taste-skill`:

- на широком экране использовать 12-колоночную асимметричную сетку: первые две карточки занимают 7 и 5 колонок, следующие - по 4; это даёт ритм без шаблонного ряда из трёх одинаковых карточек;
- количество ячеек строго равно количеству поездов, без пустых декоративных карточек;
- визуальную вариативность создавать лёгкими оттенками поверхностей у отдельных карточек, сохраняя одну цветовую систему и одинаковую структуру данных;
- не помещать все поля в отдельные вложенные карточки: регион, маршрут, дата, длительность и цена образуют типографическую иерархию внутри одной поверхности;
- действие «Подробнее» не переносится на desktop, имеет контраст не ниже WCAG AA и получает hover, focus-visible и active состояния;
- теги остаются вторичными компактными метками, не перекрывают изображения и не конкурируют с основным действием.

### 4.4. Подробная карточка поезда

Открывать подробности поверх каталога в модальном окне. Такой вариант сохраняет одностраничный сценарий и позволяет быстро вернуться к тем же фильтрам и позиции каталога.

В модальном окне показать:

- название и регион;
- полный маршрут со всеми городами;
- полное описание;
- длительность и цену «от»;
- все даты отправления в хронологическом порядке;
- полный список экскурсий;
- все теги;
- ссылку-кнопку «Купить билет».

Поведение модального окна:

- закрытие по отдельной кнопке;
- закрытие по клавише `Escape`;
- корректный заголовок и доступное имя диалога;
- перевод фокуса внутрь при открытии и возврат фокуса на вызвавшую кнопку после закрытия;
- блокировка прокрутки фоновой страницы на время открытия;
- `buy_url` открывается через `target="_blank"` с `rel="noopener noreferrer"`.
- заголовок и кнопка закрытия остаются доступны при прокрутке длинного содержимого;
- маршрут показывается как семантический горизонтальный список с допустимой локальной прокруткой, а не как декоративная схема из выдуманных станций;
- стеклянный эффект sticky-header допустим как web-аппроксимация через `backdrop-filter`, с цельным fallback-фоном при `prefers-reduced-transparency`;
- кнопки «Закрыть» и «Купить билет» не дублируют намерение других CTA, не переносят текст и имеют явные hover, focus-visible и active состояния.

## 6. Адаптивная вёрстка

### Компьютер

- ограниченный по ширине центрированный контейнер;
- фильтры в одну строку, если хватает места;
- асимметричная 12-колоночная сетка карточек на широком экране и две равные колонки на промежуточной ширине;
- модальное окно с комфортной максимальной шириной и собственной прокруткой при длинном содержимом.

### Телефон

- одна колонка карточек;
- поля поиска и фильтров на всю ширину;
- достаточно крупные области нажатия, минимум около 44 px по высоте;
- модальная карточка занимает почти весь экран и не вызывает горизонтальную прокрутку;
- длинные названия, маршруты, теги и ссылки корректно переносятся.
- split hero перестраивается в одну колонку: сначала текст, затем изображение; все многоколоночные блоки явно схлопываются в `width: 100%`;
- карточки идут строго в одну колонку, кнопки и поля не выходят за границы, основной CTA модального окна занимает доступную ширину.

Контрольные размеры для ручной проверки: примерно 1440 × 900 и 390 × 844 px.

## 7. Доступность и качество взаимодействия

- Использовать `header`, `main`, `section`, `article`, списки, заголовки, кнопки и ссылки по назначению.
- У каждого поля должен быть видимый `label`.
- Добавить заметные состояния `hover`, `focus-visible` и `active`.
- Не полагаться только на цвет для передачи состояния.
- Обновление числа результатов можно объявлять через ненавязчивую live-область.
- Проверить управление только клавиатурой: поиск, фильтры, открытие/закрытие карточки и переход к покупке.
- Любое движение должно объясняться обратной связью или сменой состояния. Анимировать только `transform` и `opacity`, не использовать обработчик `window.scroll`, постоянные циклы, marquee и scroll-hijack.
- При `MOTION_INTENSITY: 3` ограничиться короткими переходами hover/active; при `prefers-reduced-motion: reduce` убрать их и отключить smooth scroll.
- Поддержать light и dark через одни и те же семантические CSS-переменные; проверить контраст текста, полей, тегов и CTA в обоих режимах.
- Поддержать `prefers-reduced-transparency`: заменить полупрозрачные поверхности фильтров и заголовка модального окна на непрозрачные.
- Не использовать em dash и en dash в видимых строках интерфейса; для диапазонов и разделения использовать обычный дефис, точку или отдельные строки.

## 8. Тесты

### Модульные тесты утилит

- получение уникальных регионов и месяцев;
- форматирование цены, даты и длительности;
- вычисление ближайшей будущей даты;
- фильтрация по названию, региону и месяцу;
- совместная работа нескольких фильтров;
- отсутствие будущих дат.

### Компонентные и сценарные тесты

- первоначально показаны все 5 поездов;
- поиск по части названия оставляет правильную карточку;
- фильтр региона и месяца изменяет выдачу;
- сброс возвращает исходный каталог;
- пустое состояние отображается при отсутствии совпадений;
- подробная карточка открывается и содержит описание, даты, экскурсии и теги;
- подробная карточка закрывается кнопкой и клавишей `Escape`;
- ссылка покупки содержит правильный `href`, `target` и `rel`.

Тесты писать через доступные роли, подписи и видимый текст, имитируя действия пользователя с помощью `user-event`.

- light и dark сохраняют одну иерархию, фирменный красный акцент и читаемый контраст;
- при reduced motion/transparency интерфейс не теряет информацию и остаётся удобным;
- hero помещается в первый desktop-экран, CTA и подписи полей не переносятся неконтролируемо;
- нет шаблонных AI-паттернов: purple glow, трёх одинаковых feature cards, фальшивого UI-превью, декоративных status dots, scroll cue, version label и повторяющихся eyebrow над каждой секцией;
- нет em dash/en dash в видимом тексте, выдуманных чисел и сведений, которых нет в `trains.json`.

Финальный pre-flight по `taste-skill`:

- Design Read и параметры `DESIGN_VARIANCE`, `MOTION_INTENSITY`, `VISUAL_DENSITY` соответствуют реализованной странице;
- на странице используется одна тема за раз, одна акцентная цветовая семья и единое правило радиусов;
- hero, каталог, фильтры, пустое и ошибочное состояния, модальное окно образуют разные, но согласованные композиционные блоки;
- все CTA имеют уникальное намерение, однострочную подпись и достаточный контраст;
- все видимые строки перечитаны, грамматически корректны и не содержат декоративного псевдомаркетингового текста;
- изображение настоящее, локальное, имеет размеры и осмысленный alt; карточки не получают неподтверждённые изображения;
- Core Web Vitals реалистичны: LCP < 2.5 s, INP < 200 ms, CLS < 0.1;
- ни один пункт проверки доступности, адаптива и состояний не оставлен только на предположении.

- На главной странице есть каталог ровно из 5 поездов из `trains.json`.

- Страница корректно выглядит и работает на компьютере и телефоне.
- Тесты, линтер, проверка типов и production-сборка проходят без ошибок.
